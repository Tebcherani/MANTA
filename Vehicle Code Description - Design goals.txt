AUV Code — Functional Elements
Currently set up to compile under Windows (MSYS2/MinGW64) and Linux (GCC). The codebase shares the same vehicle control core between the real vehicle and the simulator; what differs between platforms is which device-driver files are linked.
Vehicle control code
The core code that runs on the vehicle. Includes the layered control mission task executor, behavior implementations (waypoint, setpoint, yo-yo, depth envelope, homing), specialized navigation functions like the LBL fix calculations, dynamic control loops for depth/heading/thrust, and sensor data acquisition. Logs all vehicle data to .obd files for post-mission review. Reads its mission script from .mi files in the Mission/ (or SMission/) directory.
Digital twin (planned)
Code that runs an onboard simulation of the vehicle in real time, parallel to the real vehicle's control loop. Used for fault detection (does the vehicle's measured behavior match what the model predicts?) and for what-if forecasting during a mission. Shares the hydrodynamic and environment models with the offline simulator below.
Environment simulator
Contains bathymetry, current fields, magnetic field, water-column parameters including sound-speed profile, and other environmental variables. Also includes models of how vehicle sensors respond to those environmental parameters (CTD, altimeter, compass, etc.). Currently bundled inside the hydrodynamic simulator (sim_bottom.c, sim_current.c, sim_conduct.c); needs to be separated out as an independent module to support multi-platform simulation, where one shared environment is sensed by multiple simulated vehicles.
Hydrodynamic simulator
Computes forces on the vehicle and integrates its trajectory using fourth-order Runge-Kutta. Requires a vehicle hydrodynamic model (added mass, drag coefficients, fin lift/drag) and actuator models (thruster characteristics, fin slew rate, transport delays, hysteresis). All of these now live as vs_* parameters in the data structure. Files: sim_main.c, sim.c, sim_bottom.c, sim_current.c, sim_conduct.c, sim_usbl.c, sensor_load.c, sim_stubs.c. (The sim_stubs.c file replaces the hardware I/O drivers used on the real vehicle, so the simulator never tries to talk to nonexistent serial ports.)
Acoustic communication simulator
Computes acoustic paths between source and receiver, time of flight, Doppler shift, and attenuation through a layered ocean. Derives bit-error rates from signal-to-noise ratio. Used for testing modem-based command-and-control and for inter-vehicle communication in multi-vehicle missions.
Failure sequencing 
Code that injects failures into the simulation on schedule. Each entry contains a triggering condition (e.g., "depth > 100 m for at least 30 s") and a sequence of resulting effects (e.g., "shift vs_xg by +0.23 m" simulating a payload shift, or "stop logging from m_compass_yaw" simulating a sensor dropout). Useful for testing fault detection and recovery logic before exposing the real vehicle to a real failure.

Data structure management code
The code uses pointers to a shared data structure (vvp) to communicate between modules rather than passing data in function calls. This means every compiled module must agree on the structure layout — definitions live in header files generated from a single source of truth, edit_struct.c. Running edit_struct on a vehicle configuration file (Sim.cfg, Xanthos.cfg, etc.) regenerates vehicle.c and vehicle.h to match.
The structure has evolved over time. The original Odyssey design partitioned sensors into a few prefixes by audience:
* m_* — measurements from physical sensors
* c_* — values commanded by the controller
* uo_* — user-overridable controller parameters set per-mission
* real_* — simulator-only "ground truth" values (true position, true buoyancy)
A more recent addition is vs_* (vehicle simulator parameters): hydrodynamic coefficients, actuator response time constants, fin geometry, and other model parameters that used to be hardcoded constants in sim.c. Promoting these to data-structure entries means they can be tuned per-mission from the .mi file and are logged into the .obd for full reproducibility — so an experiment like "what if the elevator were 4× faster?" becomes a one-line edit rather than a recompile. The pattern is general: any constant in the simulator that someone might want to vary belongs as a vs_* sensor.
Review code
Code for inspecting vehicle data logged in .obd files (and, eventually, vehicle system logs). Originally a collection of MATLAB scripts; being ported to Python as the ody_review package. The Python tools include a binary parser (handles both modern little-endian files and the original OS-9 big-endian files), a sensor inventory tool that summarizes which sensors were written and their ranges, and a growing collection of diagnostic plots: vertical-plane control behavior, horizontal-plane track and heading control, thruster activity, CTD profiles, and yo-yo classification.
